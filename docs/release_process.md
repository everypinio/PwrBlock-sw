# Versioning and release process

This project uses Git tags and GitHub Releases to publish firmware builds.

The default firmware version is stored in [`../VERSION`](../VERSION). Local and
branch builds use this value. Release builds created from Git tags use the tag
value without the leading `v`, so firmware built from `v0.2.1` reports `0.2.1`
in `*IDN?`.

## Version format

Use semantic version tags with a leading `v`:

```text
vMAJOR.MINOR.PATCH
```

Examples:

- `v0.1.0` - first public test release
- `v0.2.0` - new firmware functionality
- `v0.2.1` - bugfix release
- `v1.0.0` - stable release with a supported compatibility contract

Before `v1.0.0`, breaking behavior changes may still happen, but they should be
called out clearly in release notes.

## When to bump versions

- `MAJOR` - incompatible protocol, calibration storage, hardware, or user-visible
  behavior changes.
- `MINOR` - new compatible functionality, new SCPI commands, new USB mode
  behavior, or hardware support additions.
- `PATCH` - bug fixes, tuning changes, documentation corrections, CI fixes, or
  small compatibility fixes.

## Pre-releases

For test builds that should not be treated as stable, use pre-release tags:

```text
v0.3.0-rc.1
v0.3.0-beta.1
```

The automated release workflow marks tags that contain a hyphen as GitHub
pre-releases.

## Release artifacts

Every release tag builds both release presets:

- `release-tmc`
- `release-cdc`

The release attaches these files for each preset:

- `.bin` - raw firmware image for flashing tools that expect binary input.
- `.hex` - Intel HEX firmware image.
- `.elf` - ELF image with symbols and metadata useful for debugging.
- `.map` - linker map for memory usage inspection.
- `SHA256SUMS` - checksums for release artifact verification.

GitHub artifact attestations are generated for release artifacts so the build
provenance can be verified later.

## Release notes

Release notes are generated automatically from merged pull requests between
tags. Use PR labels to place changes into the right section:

- `firmware`, `feature`, `enhancement` - firmware behavior and feature changes.
- `fix`, `bug` - fixes.
- `hardware`, `compatibility` - hardware or compatibility notes.
- `documentation` - documentation-only changes.
- `ci`, `build`, `dependencies` - maintenance changes.
- `ignore-for-release` - exclude a PR from generated release notes.

Good release notes should mention:

- supported hardware revision, if relevant;
- USB mode impact, if relevant;
- SCPI command changes, if any;
- calibration/storage compatibility impact, if any;
- known issues or required user action.

## Changelog

Keep [`../CHANGELOG.md`](../CHANGELOG.md) updated with human-written release
history. Add user-facing changes under `Unreleased` during development, then
move them under the released version when publishing a stable release.

Autogenerated GitHub release notes are still used for each tag. The changelog is
the curated long-term history kept in the repository.

## Release checklist

Before creating a tag:

- Confirm the default branch is green in GitHub Actions.
- Confirm both `release-tmc` and `release-cdc` are expected to ship.
- Update `VERSION` to the stable version being prepared, unless the tag is a
  pre-release built from that same base version.
- Move relevant `CHANGELOG.md` entries from `Unreleased` to the release version.
- Update user-facing documentation for changed behavior.
- Make sure important PRs have useful release-note labels.
- Decide whether the release is stable or a pre-release.

Create and push a release tag:

```bash
git tag v0.1.0
git push origin v0.1.0
```

After the workflow finishes:

- Check that the GitHub Release was created.
- Check that `.bin`, `.hex`, `.elf`, `.map`, and `SHA256SUMS` are attached.
- Check that release notes are readable and mention any compatibility concerns.
- Optionally verify checksums:

```bash
sha256sum -c SHA256SUMS
```

## Hotfix releases

For a bugfix on top of the latest release, merge the fix into the default branch
and publish the next patch tag, for example `v0.2.2`.

If a fix must be made from an older release line, create a branch from the old
tag, cherry-pick the fix, and publish the next patch tag from that branch.
